> **Category:** Lossy
> **File Extensions:** `.gsm`, `.wav` (with Microsoft GSM codec), `.raw`
> **MIME Types:** `audio/x-gsm`, `audio/gsm`, `audio/x-wav`
> **Standardization Body:** ETSI (European Telecommunications Standards Institute)
> **Primary Specification:** ETSI EN 300 961 (GSM 06.10); 3GPP TS 46.010 (current version)
> **Patent Status:** Patented — licensed via Via Licensing Corporation (GSM patents)
> **License:** Royalty-bearing for commercial use; 3GPP-essential patents

## 1. HISTORICAL CONTEXT & ORIGIN

### 1.1 Creation & Motivation
- **Creator(s):** ETSI (European Telecommunications Standards Institute), GSM MoU Association
- **Year Created:** 1991 (standardized as GSM 06.10, published as ETS 300 961)
- **Original Purpose:** Define the mandatory speech transcoding algorithm for the GSM Full Rate (FR) traffic channel (TCH/F). This was the first digital speech coding standard designed specifically for digital cellular mobile telephony, replacing the analog FM transmission of the first-generation (1G) mobile networks. The codec needed to compress 13-bit, 8 kHz PCM voice into a 13 kbps bitstream suitable for transmission over the GSM radio channel.
- **Problem with Predecessors:** The predecessor was analog FM modulation (NMT, AMPS, TACS), which provided poor quality, limited capacity, and no security. GSM 06.10 provided digital voice quality, encryption, and significantly higher spectral efficiency. Compared to the 64 kbps G.711 PCM used in PSTN, GSM 06.10 achieves an 8:1 compression ratio.

### 1.2 Version History
| Version | Year | Key Changes |
|---------|------|-------------|
| GSM 06.10 v3.0.0 | 1991 | Initial specification, Phase 1 GSM |
| GSM 06.10 v6.0.0 | 1997 | GSM Phase 2+, clarifications |

### 1.3 Current Adoption
- **Primary use cases today:** GSM cellular networks (2G), legacy VoIP, voicemail systems, some military communications, legacy Asterisk VoIP gateways, early internet voice applications
- **Platforms with native support:** All GSM mobile phones (2G), Linux (libgsm), macOS (libgsm), embedded systems, some VoIP gateways
- **Major services using this format:** All GSM 2G voice calls (in the radio link), early SIP/VoIP services, some satellite phone systems
- **Hardware support:** Integrated into baseband processors in 2G-capable mobile phones; most modern phones use AMR (not GSM 06.10) for voice over 3G/4G/5G
- **Status:** Legacy — GSM 06.10 is being phased out as carriers refarm 2G spectrum for LTE and 5G. However, billions of devices still support it, and GSM 06.10 remains the reference for GSM full-rate voice. AMR and AMR-WB have replaced it in 3G+ networks.

## 2. TECHNICAL ARCHITECTURE OVERVIEW

### 2.1 Codec Family & Algorithm Class
- **Codec type:** Parametric speech coder — RPE-LTP (Regular Pulse Excitation-Long Term Prediction)
- **Core algorithm:** RPE-LTP, which combines linear predictive coding (LPC), long-term prediction (LTP), and regular pulse excitation (RPE) in a hybrid structure
- **Loss mechanism:** Perceptual quantization of RPE pulses; coarse quantization of LPC and LTP parameters
- **Frame-based vs sample-based:** Frame-based encoding; fixed 20 ms frames
- **Fixed vs variable frame size:** Fixed 20 ms frames, fixed 260-bit output

### 2.2 High-Level Encoding Flow (Block Diagram)
```
Input: 13-bit uniform linear PCM (8 kHz, 160 samples per frame)
      │
      ▼
[Pre-processing: Offset compensation → Pre-emphasis filter (H(z)=1−0.68z⁻¹)]
      │
      ▼
[LPC Analysis (once per frame, 20 ms)]
      │   Hamming window, 8th order Levinson-Durbin
      │   → LAR (Log-Area Ratio) coefficients
      ▼
[LAR Quantization and Coding: 36 bits]
      │
      ▼
[Segmentation into 4 subframes (5 ms each, 40 samples)]
      │
      ▼
[For each subframe:]
      │
      ├──[Long Term Prediction (LTP)]
      │       LTP lag search (40–160 samples), gain quantization
      │       → LTP parameters: 36 bits total (7+2+7+2+7+2+7+2)
      │
      └──[RPE Encoding (per subframe)]
              Weighted residual signal → Grid selection (3 positions)
              → 13 pulse amplitudes × 3 bits each = 39 bits
              → Block amplitude = 6 bits
              → Total RPE: 188 bits per frame
      ▼
[Bit Reordering per GSM 05.03 importance ranking]
      │
      ▼
[Output: 260 bits per 20 ms frame = 13.0 kbps]
```

### 2.3 Key Design Parameters
| Parameter | Value | Notes |
|-----------|-------|-------|
| Algorithmic delay | 20 ms frame + 5 ms lookahead | ~25 ms total |
| Frame size | 160 samples (20 ms at 8 kHz) | |
| Bitrate | 13.0 kbps (260 bits / 20 ms) | |
| Max channels | 1 (mono) | |
| Max bit depth | 13-bit linear PCM input | Internal: 16-bit arithmetic |
| Max sample rate | 8 kHz | Input and output |
| Bandwidth | 300–3,400 Hz (narrowband) | Same as GSM voice channel |
| Complexity | ~4 MIPS encoder, ~2 MIPS decoder | Low complexity design |
| MOS Score | ~3.6–3.8 | Lower quality than AMR (3.9–4.1) |

## 3. BINARY FORMAT SPECIFICATION

### 3.1 GSM 06.10 Frame Bit Allocation

Per GSM 06.10 / 3GPP TS 46.010, each 20 ms speech frame (260 bits) is organized as follows:

```
Bit Layout — GSM 06.10 Frame (260 bits total):

=== LAR (Log-Area Ratio) Parameters — 36 bits ===
Bit 1–6:    LAR 1  (6 bits)
Bit 7–12:   LAR 2  (6 bits)
Bit 13–17:  LAR 3  (5 bits)
Bit 18–22:  LAR 4  (5 bits)
Bit 23–26:  LAR 5  (4 bits)
Bit 27–30:  LAR 6  (4 bits)
Bit 31–33:  LAR 7  (3 bits)
Bit 34–36:  LAR 8  (3 bits)

=== Subframe 1 (5 ms, 40 samples) ===
Bit 37–43:  LTP lag N1  (7 bits)
Bit 44–45:  LTP gain b1 (2 bits)
Bit 46–48:  RPE grid M1  (2 bits) — selects 1 of 3 positions
Bit 49–54:  Block amplitude Xmax1 (6 bits)
Bit 55–57:  Pulse x1[0]  (3 bits)
Bit 58–60:  Pulse x1[1]  (3 bits)
Bit 61–63:  Pulse x1[2]  (3 bits)
... (continues for pulses x1[0..12])

=== Subframe 2 (5 ms, 40 samples) ===
Bit 93–99:  LTP lag N2  (7 bits)
Bit 100–101: LTP gain b2 (2 bits)
Bit 102–103: RPE grid M2  (2 bits)
Bit 104–109: Block amplitude Xmax2 (6 bits)
Bit 110–148: RPE pulses x2[0..12] (39 bits)

=== Subframe 3 (5 ms, 40 samples) ===
Bit 149–155: LTP lag N3  (7 bits)
Bit 156–157: LTP gain b3 (2 bits)
Bit 158–159: RPE grid M3  (2 bits)
Bit 160–165: Block amplitude Xmax3 (6 bits)
Bit 166–204: RPE pulses x3[0..12] (39 bits)

=== Subframe 4 (5 ms, 40 samples) ===
Bit 205–211: LTP lag N4  (7 bits)
Bit 212–213: LTP gain b4 (2 bits)
Bit 214–215: RPE grid M4  (2 bits)
Bit 216–221: Block amplitude Xmax4 (6 bits)
Bit 222–260: RPE pulses x4[0..12] (39 bits)

Total: 36 (LAR) + 36 (LTP × 4 subframes) + 188 (RPE × 4 subframes) = 260 bits
```

### 3.2 GSM 06.10 File Format (.gsm)
Raw GSM bitstream (.gsm):

```

-------  ------  --------------------  ----------------------------------
0x0000   33     First frame            First GSM frame (260 bits = 33 bytes)

Some implementations use the "GSM file format" where each frame is preceded by a frame header byte, making it 34 bytes per frame.

## 4. ENCODING ALGORITHM — DEEP DETAIL

### 4.1 Pre-Processing Stage
- **Offset compensation:** Removes DC offset by subtracting the mean of the input samples (computed over the frame)
- **Pre-emphasis filter:** H(z) = 1 − 0.68·z⁻¹, a first-order high-pass filter that emphasizes high-frequency speech components. This improves the accuracy of LPC analysis.
- **Windowing function:** Hamming window applied to the 20 ms frame before autocorrelation computation
- **Level normalization:** Not explicitly applied; the RPE amplitude normalization handles relative levels

### 4.2 Analysis / Transform Stage

#### 4.2.1 LPC Analysis (8th Order)
```
Parameters:
  LPC order:        8 (8th order linear prediction)
  Window:           Hamming window (160 samples)
  Algorithm:        Autocorrelation method + Levinson-Durbin recursion
  Coefficient precision:  16-bit fixed point in reference implementation
  Update frequency:  Once per 20 ms frame
  Output:           LAR (Log-Area Ratio) coefficients

LAR computation:
  1. Compute autocorrelation r[0..8] from windowed frame
  2. Apply lag windowing to stabilize Levinson-Durbin
  3. Levinson-Durbin recursion → LPC coefficients a[1..8]
  4. Convert reflection coefficients rc[1..8] → LAR[1..8]
  5. Quantize and code LAR[1..8] to 36 bits

LAR quantization:
  - Each LAR is quantized with a non-uniform scalar quantizer
  - Different quantizer for each LAR coefficient
  - Quantizer tables optimized for GSM speech characteristics
```

#### 4.2.2 Long Term Prediction (LTP)
```
Per subframe (5 ms = 40 samples):

LTP lag search (closed-loop):
  - Search range: lag = 40 to 160 samples (5 to 20 ms at 8 kHz)
  - Method: Cross-correlation of weighted residual with past weighted residual
  - Resolution: Integer samples (no fractional pitch)
  - Search criterion: Maximize normalized cross-correlation
    argmax_lag { |Σ e[n]·e[n−lag]| } where e[n] = pre-processed residual

LTP gain quantization:
  - 4 levels: 0.0, 0.2, 0.5, 0.9 (approximate values)
  - 2-bit quantization
  - Gain applied to past excitation: b × excitation[n−lag]

LTP synthesis:
  excitation[n] = rpe_excitation[n] + b × excitation[n−lag]
```

#### 4.2.3 Regular Pulse Excitation (RPE)
```
Per subframe (5 ms = 40 samples):

Step 1 — Weighting filter:
  - Apply perceptual weighting filter W(z) = A(z/γ) / A(z/γ²)
  - γ ≈ 0.8 (weighting factor)
  - Produces weighted residual signal

Step 2 — RPE grid selection:
  - Divide 40-sample sequence into 3 possible subsequences:
      Grid 0: samples at positions 0, 3, 6, ..., 39  (14 positions)
      Grid 1: samples at positions 1, 4, 7, ..., 37  (13 positions)
      Grid 2: samples at positions 2, 5, 8, ..., 38  (13 positions)
  - Select grid M with maximum energy: Σ (x[n])²
  - Transmit M as 2-bit code (0, 1, or 2)

Step 3 — Block amplitude quantization:
  - Find Xmax = max |x[n]| over selected grid positions
  - Quantize Xmax with 6-bit log-PCM quantizer
  - Logarithmic step sizes for better perceptual quality

Step 4 — Pulse amplitude quantization:
  - Normalize pulses: x_norm[n] = x[n] / Xmax
  - Quantize each normalized pulse: 3 bits per pulse (−3 to +3)
  - 13 pulses × 3 bits = 39 bits
  - Total RPE bits per subframe: 2 (grid) + 6 (amplitude) + 39 (pulses) = 47 bits
```

### 4.3 Complete Bit Allocation Summary

```
Frame structure (20 ms, 160 samples, 260 bits):

LPC/LAR parameters:    36 bits  (8 coefficients, non-uniform quantization)
LTP parameters:        36 bits  (4 subframes × 7 bits lag + 4 × 2 bits gain)
RPE parameters:        188 bits  (4 subframes × 47 bits)
  └── Grid selection:  8 bits   (4 × 2 bits)
  └── Block amplitude: 24 bits  (4 × 6 bits)
  └── Pulse amplitudes: 156 bits (4 × 13 × 3 bits)

Total: 36 + 36 + 188 = 260 bits
Bitrate: 260 bits / 20 ms = 13.0 kbps
```

## 5. DECODING ALGORITHM — DEEP DETAIL

### 5.1 Stream Synchronization & Seeking

#### Sync Strategy
```
Raw GSM (.gsm):
  1. Each frame is 33 bytes (260 bits = 33 bytes, last 4 bits unused)
  2. Frame index = byte_offset / 33
  3. No sync word — alignment is implicit from frame boundaries
  4. Read 33 bytes, extract 260 bits, decode

Microsoft GSM WAV:
  1. Each block is 65 bytes (320 samples encoded)
  2. Block index = byte_offset / 65
  3. Decode 320 samples per block
```

#### Seeking
```
Random access:
  - GSM frames are all identical size (33 bytes)
  - Frame index = target_time_ms / 20
  - Byte offset = frame_index × 33
  - Precision: ±20 ms (frame-accurate)
```

### 5.2 Core Decode Pipeline
```
1. Read GSM frame (33 bytes = 260 bits)

2. Parse bitstream:
   ├── Dequantize and decode LAR[1..8] → reflection coefficients → LPC
   ├── For each of 4 subframes (5 ms each):
   │   ├── Decode LTP lag (7 bits) → lag N
   │   ├── Decode LTP gain (2 bits) → gain b
   │   ├── Decode RPE grid (2 bits) → grid position M
   │   ├── Decode block amplitude (6 bits) → Xmax
   │   └── Decode 13 pulse amplitudes (39 bits) → x_pulse[0..12]
   │
   │   ├── Reconstruct RPE sequence at selected grid positions
   │   ├── Denormalize: x[n] = x_pulse[n] × Xmax / 3
   │   ├── Interleave zeros at non-selected grid positions (40 samples total)
   │   └── Compute LTP contribution: excitation[n] = x[n] + b × excitation[n−N]
   │
   └── Reconstruct full excitation for 4 subframes

3. Apply short-term synthesis filter (LPC):
   For each sample in subframe:
     s[n] = excitation[n] + Σ(i=1 to 8) a[i] × s[n−i]

4. Apply de-emphasis filter:
   H(z) = 1 / (1 − 0.68·z⁻¹)   [inverse of pre-emphasis]

5. Post-processing:
   ├── First-order high-pass filter (cutoff ~80 Hz)
   └── Apply appropriate scaling for 16-bit output

6. Output: 160 samples × 16-bit linear PCM (8 kHz)
```

### 5.3 Error Concealment
- **Corrupt frame detection:** GSM channel coding (GSM 05.03) provides error detection and correction. In raw GSM files, corrupted frames may be detected by invalid LAR values or out-of-range parameter values.
- **Concealment method:** Frame repetition — repeat the last good frame's parameters with gradual attenuation. For multiple bad frames, progressively mute the output.
- **Maximum consecutive errors before silence:** Typically 3–5 frames, then mute.

### 8.3 FFmpeg Encoding — libavcodec C API

```c
#include <libavcodec/avcodec.h>
#include <libavformat/avformat.h>
#include <libavutil/opt.h>
#include <libswresample/swresample.h>

// ─── 1. Find encoder ─────────────────────────────────────────────────────────
const AVCodec *codec = avcodec_find_encoder(AV_CODEC_ID_GSM);
if (!codec) { fprintf(stderr, "GSM encoder not found\n"); exit(1); }

// ─── 2. Allocate codec context ────────────────────────────────────────────────
AVCodecContext *ctx = avcodec_alloc_context3(codec);
if (!ctx) { fprintf(stderr, "OOM\n"); exit(1); }

// ─── 3. Set required parameters ────────────────────────────────────────────────
ctx->bit_rate    = 13000;             // bits/sec (13 kbps fixed)
ctx->sample_fmt  = AV_SAMPLE_FMT_S16; // GSM accepts signed 16-bit PCM
ctx->sample_rate = 8000;              // Hz — MUST be 8000 for GSM 06.10
av_channel_layout_default(&ctx->ch_layout, 1); // Mono

// ─── 4. Open codec ─────────────────────────────────────────────────────────
int ret = avcodec_open2(ctx, codec, NULL);
if (ret < 0) {
    char errbuf[128]; av_strerror(ret, errbuf, sizeof(errbuf));
    fprintf(stderr, "avcodec_open2 failed: %s\n", errbuf);
    exit(1);
}

// ─── 5. Allocate frame and packet ────────────────────────────────────────────
AVFrame  *frame = av_frame_alloc();
frame->format      = ctx->sample_fmt;
frame->sample_rate = ctx->sample_rate;
av_channel_layout_copy(&frame->ch_layout, &ctx->ch_layout);
frame->nb_samples  = ctx->frame_size; // GSM frame: 160 samples (20 ms at 8 kHz)
av_frame_get_buffer(frame, 0);

AVPacket *pkt = av_packet_alloc();

// ─── 6. Encode loop ───────────────────────────────────────────────────────────
void encode_frame(AVCodecContext *ctx, AVFrame *frame, AVPacket *pkt, FILE *outfile) {
    int ret = avcodec_send_frame(ctx, frame);
    if (ret < 0) { /* handle AVERROR(EAGAIN), AVERROR(EINVAL) */ }

    while (ret >= 0) {
        ret = avcodec_receive_packet(ctx, pkt);
        if (ret == AVERROR(EAGAIN) || ret == AVERROR_EOF) return;
        if (ret < 0) { /* fatal error */ exit(1); }
        // GSM output: 33 bytes per frame (260 bits)
        fwrite(pkt->data, 1, pkt->size, outfile);
        av_packet_unref(pkt);
    }
}

// ─── 7. Flush encoder ─────────────────────────────────────────────────────────
encode_frame(ctx, NULL, pkt, outfile); // NULL frame triggers flush/drain

// ─── 8. Cleanup ───────────────────────────────────────────────────────────────
av_frame_free(&frame);
av_packet_free(&pkt);
avcodec_free_context(&ctx);
```

**Critical Notes:**
- GSM 06.10 requires exactly 8000 Hz input; resample to 8000 Hz before encoding
- `ctx->frame_size` is 160 samples per frame (20 ms)
- GSM encoder output is always 33 bytes per frame
- GSM accepts `AV_SAMPLE_FMT_S16` input
- No VBR or quality setting — GSM 06.10 is always 13 kbps

```c
// ─── Complete decode program skeleton ────────────────────────────────────────
AVFormatContext *fmt_ctx = NULL;
avformat_open_input(&fmt_ctx, "input.gsm", NULL, NULL);
avformat_find_stream_info(fmt_ctx, NULL);

// Find audio stream
int audio_idx = av_find_best_stream(fmt_ctx, AVMEDIA_TYPE_AUDIO, -1, -1, NULL, 0);
AVStream *stream = fmt_ctx->streams[audio_idx];

// Find and open decoder

AVCodecContext *dec_ctx = avcodec_alloc_context3(dec);
avcodec_parameters_to_context(dec_ctx, stream->codecpar);

AVFrame  *frm = av_frame_alloc();

    if (pkt->stream_index == audio_idx) {
        ret = avcodec_send_packet(dec_ctx, pkt);
        if (ret < 0) { /* handle error */ }
        while (avcodec_receive_frame(dec_ctx, frm) == 0) {
            // frm->data[0] = PCM samples (S16 format)
            // frm->nb_samples = 160 (one GSM frame = 20 ms)
            // frm->sample_rate = 8000
            process_audio_frame(frm);
            av_frame_unref(frm);
        }
    }
    av_packet_unref(pkt);
}

// Flush decoder
avcodec_send_packet(dec_ctx, NULL);
while (avcodec_receive_frame(dec_ctx, frm) == 0) {
    process_audio_frame(frm);
    av_frame_unref(frm);
}

// Cleanup
av_frame_free(&frm);
av_packet_free(&pkt);
avcodec_free_context(&dec_ctx);
avformat_close_input(&fmt_ctx);
```

## 14. KNOWN ISSUES, BUGS & EDGE CASES

### 14.1 FFmpeg Encoder-Specific Issues
| Issue | FFmpeg Versions Affected | Workaround |
|-------|--------------------------|------------|
| libgsm not compiled in FFmpeg | Many | Build with `--enable-libgsm` |
| Microsoft GSM vs raw GSM | All | Use `gsm_ms` codec for WAV, `libgsm` for raw |
| 8-bit clean GSM format | All | Raw GSM is not 8-bit clean; may contain 0x00 bytes |

### 14.2 Interoperability Issues
- **libgsm vs Microsoft GSM:** These use different bit ordering and framing. Microsoft GSM WAV stores 320 samples per 65-byte block (40 ms), while raw GSM stores 160 samples per 33-byte frame (20 ms). FFmpeg's `libgsm` decoder handles raw GSM; `gsm_ms` handles Microsoft WAV.
- **0x00 bytes in GSM stream:** Raw GSM frames can contain null bytes, which some text-based tools may strip or misinterpret. Use binary-safe tools.
- **A-law / μ-law input:** GSM decoder outputs 16-bit linear PCM. Input can be A-law or μ-law PCM via the G.711 conversion table (built into GSM).

### 14.3 Edge Cases to Handle in Converter
- **Empty file / 0-sample stream:** Produce empty output file with proper headers
- **File < 1 frame (33 bytes):** Encode as single frame with zero padding
- **All-silence audio:** GSM of silence produces structured output (no special concealment)
- **Corrupt frame:** Decoder may produce distorted audio; handle gracefully
- **Sample rate not 8 kHz:** FFmpeg resamples to 8000 Hz
